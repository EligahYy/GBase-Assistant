三种语义映射方案对比

从"销售额"到 order.pay_amount，LLM 如何准确理解业务含义？

方案 A：轻量增量改进

不改架构，补齐缺失的信息传递环节
用户: "查询最近一个月销售额"
        │
        ▼
┌─────────────────────────────────────┐
│ Schema Grounding (关键词精确匹配)      │
│ → 匹配: "销售" → sale 表              │
│ → 匹配: "额" → amount 列(2-gram)     │
└──────────────┬──────────────────────┘
               ▼
┌─────────────────────────────────────┐
│ 🆕 Prompt 增强                    │
│ 注入: COMMENT label + 枚举值 + 列角色  │
│ sale.amount: "订单金额(元)" MEASURE   │
│ sale.created_at: "创建时间" TIME_DIM  │
│ sale.status: 0=待支付 1=已支付 ENUM   │
└──────────────┬──────────────────────┘
               ▼
┌─────────────────────────────────────┐
│ LLM SQL 生成 (DeepSeek)              │
│ 🆕 启用 Few-shot 示例            │
│ 🆕 Grounded tables 交集→并集     │
│ SELECT SUM(amount) FROM sale         │
│ WHERE created_at >= DATE_SUB(...)    │
└──────────────┬──────────────────────┘
               ▼
          验证 → 执行 → 🆕 ECharts 图表

优点

  • 改动最小，2-3 天可完成
  • 充分利用已解析的 DDL 元数据
  • 风险低，不改变现有架构

缺点

  • "销售额"→amount 的映射仍靠 LLM 猜 + 关键词命中
  • COMMENT 质量决定上限
  • 对复杂业务术语（同比、环比）无结构化支持

方案 B：业务词汇表 + 统一 Grounding（推荐）

新建 Business Glossary 层 + RRF 融合检索
用户: "查询最近一个月销售额"
        │
        ▼
┌─────────────────────────────────────────────────┐
│ 🆕 统一 Schema Grounding (RRF 多策略融合)      │
│                                                  │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────┐ │
│  │ 精确匹配(L1) │ │ 向量语义(L2) │ │🆕 业务词│ │
│  │ sale, amount │ │ order, price │ │汇(L0)  │ │
│  │ score=1.0    │ │ score=0.85   │ │销售额→  │ │
│  │              │ │              │ │sale.amt│ │
│  └──────┬───────┘ └──────┬───────┘ └─────┬────┘ │
│         └────────────────┼───────────────┘      │
│                   RRF 融合排序                    │
│              → grounded_tables + columns         │
└──────────────────────┬──────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────┐
│ 🆕 Business Glossary (YAML 配置)              │
│                                                  │
│ terms:                                           │
│   销售额: {table: sale, column: pay_amount}       │
│   上月: {sql_template: "DATE_SUB(CURDATE(), ...)"}│
│   环比: {type: computed, formula: "..."}          │
│                                                  │
│ 自动提取: DDL COMMENT → 候选映射 → 人工确认     │
│ 手动补充: YAML 配置文件覆盖/扩展                │
└──────────────────────┬──────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────┐
│ LLM Prompt (完整上下文)                           │
│ ① Business Glossary 匹配结果                      │
│ ② Schema DDL + COMMENT + 枚举值 + 列角色          │
│ ③ Few-shot 相似示例 (Qdrant)                     │
│ ④ 🆕 图表建议指令 (输出 chart_config)              │
└──────────────────────┬──────────────────────────┘
                       ▼
          SQL + chart_config → 验证 → 执行
                       ▼
          🆕 ECharts 渲染 + 自然语言解读

优点

  • "销售额"→sale.pay_amount 可精确命中
  • 支持业务术语的同义词扩展
  • 多策略融合比单一策略鲁棒
  • 自动提取降低维护成本

缺点

  • 需要新建 Glossary 配置体系(~5 天)
  • RRF 融合需要调参
  • 初始建库需要 DBA 审核映射

方案 C：重型语义层

类似 Cube.js / dbt Metrics 的完整语义层
cubes:
  - name: sales_analysis
    sql: SELECT * FROM sale
    measures:
      - name: total_revenue
        sql: pay_amount
        type: sum
      - name: avg_order_value
        sql: pay_amount
        type: avg
    dimensions:
      - name: created_at
        sql: created_at
        type: time
        granularities: [day, week, month, quarter, year]
      - name: status
        sql: status
        type: string

优点

  • 最强大、最精确
  • 支持复杂计算（同比、环比、聚合）

缺点

  • 太重，适合 50+ 表的成熟数仓
  • 初始配置成本高(2-3 周)
  • 每个新指标需要定义
  • 当前项目规模不需要
