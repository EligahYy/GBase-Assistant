Semantic Mapper Agent — 准确度保证 & 评估体系

三层约束 + 自动评估 + Orchestrator 监管

一层：Agent 自身的约束机制

Agent 系统提示词内置的硬约束
SYSTEM PROMPT (Semantic Mapper):

1. Schema-First 原则: 所有映射必须引用真实存在的表/列，
   禁止凭空猜测列名。不确定时调用 get_table_profile() 确认。

2. 置信度自评: 每次输出必须包含 confidence 评分(0-1)：
   - >=0.9: Glossary 精确命中 + Schema 交叉验证通过
   - 0.7-0.9: 通过列名+COMMENT 推理，语义高度匹配
   - 0.5-0.7: 仅向量语义相似，需人工确认
   - <0.5: 放弃映射，标记为 unknown

3. 逐步验证: 每步 Action 后必须验证 Observe 结果，
   不跳过任何验证步骤。

二层：Orchestrator 监管

Orchestrator 作为 Semantic Mapper 的"管理者"
Orchestrator 调用 Semantic Mapper 后执行监管检查：

┌─────────────────────────────────────────────────┐
│ Orchestrator Supervisor Check:               │
│                                                  │
│ ① Schema 校验: 映射的表/列是否真实存在？          │
│    → 调用 SchemaGraph.validate_mapping()         │
│                                                  │
│ ② 置信度门控:                                   │
│    confidence >= 0.7 → 直接传给 SQL Specialist     │
│    confidence 0.5-0.7 → 传给 SQL Spec + 标记低置信度│
│    confidence < 0.5 → 反问用户确认              │
│    "您说的'销售额'是指 product_sale.pay_amount 吗？"│
│                                                  │
│ ③ 完整性检查: 映射是否覆盖了问题中的所有关键术语？  │
│    缺失的术语 → 标记为 unresolved_terms            │
└─────────────────────────────────────────────────┘

三层：SQL 执行后的验证闭环

SQL 执行结果反向验证语义映射是否正确
SQL 执行后自动检查：

结果合理性检查 (Result Sanity Check):
  ✗ 空结果 → 可能是语义映射错误(选了错的表/列)
  ✗ 全是 NULL → 列映射可能不对
  ✗ 数值异常(如金额负数、数量极大) → 可能是度量选错
  ✓ 有正常数据 → 映射大概率正确

用户隐式反馈收集:
  • 用户复制了结果 → +1 正向信号
  • 用户追问/纠正("不是这个") → 负向信号，记录为 bad case
  • 用户点赞/点踩 → 直接反馈

指标:
  • Table Recall: 命中率 (期望表 ∩ 映射表)
  • Column Precision: 列精确率
  • Term Mapping Accuracy: 业务术语映射正确率
  • End-to-End: SQL 执行成功率

运行: pytest tests/semantic_mapper/ (CI 集成)
